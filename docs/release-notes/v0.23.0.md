Vibeke 0.23.0 keeps the state database small and fast. Commands such as `vibeke server status` no longer hang when an agent session has a long history.

## New in this release

### The server stays responsive with a long agent history

Vibeke stores every agent tool call in its state database. Earlier versions searched all of these records each time a tool call ended. With a long history, each search took about half a second. During that time, the server could not answer other requests. When the computer was short of memory, a search could take much longer, and commands such as `vibeke server status` seemed to hang. Vibeke now uses database indexes for these searches, so they are fast at any history size.

### The database and its write-ahead log stay small

SQLite, the database that Vibeke uses, first writes changes to a separate file called the write-ahead log (WAL). Earlier versions never made this file smaller. After a large cleanup, it could stay over 1 GB. Deleted records also left empty space inside the database file.

- The write-ahead log is now cut back to at most 64 MB.
- After the hourly cleanup, Vibeke gives empty space back to the disk and empties the write-ahead log.
- Large cleanups now delete records in small batches.
- A database from an older version is rebuilt once after the update. On one test database, this reduced the file from 2.0 GB to 580 MB.

### Old history is removed

- Agent history is now kept for 90 days by default (`events.history_retention`).
- Observed tool calls and turns of runs that are not part of a task are removed after the same time. Records of task runs stay, because task reviews use them. Only `vibeke forget` removes those.
- Closed collision warnings are removed after the same time. Vibeke also keeps at most the 200 newest ones, which is all that the collision view shows.

### Commands wait for a server that is still starting

When the server holds the session but does not answer yet, for example during a database upgrade, commands now wait up to two minutes. They print one line that says why they wait. Before, they stopped with an error after 5 or 10 seconds.

### Dependency security updates

The bundled SQLite and the `tokio`, `zstd`, `rustix`, `crypto-bigint` and `ctutils` libraries are updated for recently published security advisories.

## Install the terminal CLI

Available for **macOS 13 or later on Apple silicon or Intel** and **Linux on x86_64 or ARM64**.
Install `minisign` first (`brew install minisign` on macOS, or your Linux package manager), then run:

```sh
curl -fsSL https://vibeke.dev/install.sh | VIBEKE_VERSION=0.23.0 sh
```

The installer verifies the release signature, checksum, and version, and installs inside your home directory.
Add `~/.local/bin` to your `PATH` if needed.

Start in your project:

```sh
cd your-project
vibeke
```

Complete first-run setup, then run `claude`, `codex`, or your usual agent command in a pane.
Press **Ctrl+B** and wait to see every key, or press **Ctrl+B**, then **:** to open the command palette.

[Installation guide](https://vibeke.dev/docs/install) · [Your first workspace](https://vibeke.dev/docs/quickstart)

## Desktop app

The 0.23.0 desktop packages are not part of this release yet: they follow when Apple's notarization service is available again. The 0.22.0 desktop app works with a 0.23.0 host, because the render protocol and JSON API are unchanged. Until then, an update check in the desktop app reports that the release has no desktop download for your platform.

## Use your phone or browser

Open [app.vibeke.dev](https://app.vibeke.dev). With a Vibeke session running on your host, open the TUI **Devices** view (`prefix+alt+d`, or **Pair a phone** in the command palette), or run:

```sh
vibeke gateway pair
```

Scan the QR code or open the link, then compare and confirm the device fingerprint.
The server manages the gateway after setup.

[Phone and browser guide](https://vibeke.dev/docs/mobile) · [Sharing and handoffs](https://vibeke.dev/docs/handoff)

## Upgrading and limitations

- Update with `vibeke update`, or with **Update Vibeke…** in the command palette. From 0.14.1 or older, run the installer once instead (see the 0.14.2 notes).
- The first start after the update adds indexes to the state database. On a large database this takes a few seconds. About 30 seconds after the server starts, it also rebuilds the database once. While the rebuild runs (a few seconds for a few hundred MB), commands wait for it.
- The rebuild needs free disk space of about the size of the data that remains, plus a backup copy that the migration writes to `~/.local/state/vibeke/<session>/backups/`.
- The default for `events.history_retention` is now 90 days instead of 365 days. Agent history, observed tool calls of runs without a task, and closed collision warnings older than this are removed. To keep more, set `history_retention = "365d"` under `[events]` in `config.toml`.
- After you update, you cannot go back to a version older than 0.23.0 with this state database, because its schema changed. `vibeke update` refuses such a downgrade. The migration keeps a backup that `vibeke doctor --restore-backup` can restore.
- 0.23.0 keeps the render protocol and JSON API compatible with 0.22.0.
- Running pane processes survive a server restart. Restart the TUI client to load the new version.
- Linux host CLI binaries use static musl linking.
